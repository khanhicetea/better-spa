# Kysely to Drizzle ORM 1.0 RC Migration Plan

## Decision and scope

Replace Kysely with Drizzle ORM across the database package, repositories, Better Auth,
Node runtime, and Cloudflare Worker runtime. Preserve the current PostgreSQL schema and
all application behavior; this is an ORM and migration-tooling change, not a product or
schema redesign.

Target prerelease versions at planning time (2026-07-28):

- `drizzle-orm@1.0.0-rc.4`
- `drizzle-kit@1.0.0-rc.4`
- `@better-auth/drizzle-adapter@1.7.0-rc.2`
- the complete Better Auth package family at `1.7.0-rc.2`

Pin prereleases exactly. Do not use ranges or floating `@rc` tags in manifests. Better
Auth 1.6.18's Drizzle adapter only declares support for `drizzle-orm@^0.45.2`; Better Auth
1.7 RC is required because its adapter supports Drizzle `>=1.0.0-rc.1 <2.0.0`.

## Non-goals

- No application feature, RPC contract, route, or UI changes.
- No database table, column, index, constraint, or data changes.
- No relational-query API until a real query needs it.
- No `drizzle-kit push` in shared, staging, or production environments.
- No new seed files or test suite.
- Do not recreate the current large generic repository abstraction in Drizzle.

## Required invariants

- SQL table names remain singular and columns remain `snake_case`.
- TypeScript properties remain `camelCase`.
- All five live tables remain exact: `user`, `session`, `account`, `verification`, and
  `todo_item`.
- Existing defaults, nullability, foreign keys, cascade behavior, indexes, and index names
  remain exact.
- IDs continue to be generated by Better Auth or application callers, not the database.
- RPC dates remain ISO strings; database timestamps remain JavaScript `Date` values.
- Writes continue through oRPC or Better Auth's HTTP/server API boundaries.
- Ownership remains part of todo update/delete SQL predicates.
- Node owns one process-level database resource and closes it during graceful shutdown.
- Workers create a request-scoped `pg.Client` from `env.HYPERDRIVE.connectionString`,
  connect it, and close it in `finally`. Never cache a Worker client or Drizzle instance
  globally.
- Query logs must not include SQL text, parameters, credentials, cookies, or tokens.

## Phase 1: compatibility spike and version lock

1. Create a dedicated migration branch and freeze schema changes until cutover.
2. Update `pnpm-workspace.yaml` with exact catalog entries for Drizzle ORM, Drizzle Kit,
   and the aligned Better Auth RC packages.
3. Update package manifests:
   - `packages/db/package.json`: replace `kysely`/`kysely-ctl` with `drizzle-orm` and
     `drizzle-kit`; retain `pg`; remove `tsup` if migrations no longer need bundling.
   - `packages/auth/package.json`: add `@better-auth/drizzle-adapter`; remove direct
     Kysely; align `better-auth`, `@better-auth/core`, `@better-auth/expo`, and
     `@better-auth/utils` to the 1.7 RC-compatible versions.
4. Install and inspect peer-dependency output. Treat any unmet Drizzle, Better Auth, `pg`,
   or TypeScript peer as a blocker rather than suppressing it.
5. Run the Better Auth 1.7 upgrade review. The currently enabled admin, Expo, GitHub, and
   Google paths should not require an intentional schema change, but generated schema and
   auth behavior must be compared before continuing.
6. Commit the lockfile with exact RC resolutions. Evaluate each later RC upgrade on a
   database clone before changing the pins.

**Gate:** both Node and Worker can import the pinned packages, and all Better Auth peers
are satisfied.

## Phase 2: establish the Drizzle schema as the source of truth

1. Add `packages/db/drizzle.config.ts` with:
   - PostgreSQL dialect;
   - `packages/db/src/schema/**/*.ts` as the schema input;
   - `packages/db/drizzle/` as migration output;
   - `DATABASE_URL` for CLI-only migration access;
   - `schemaFilter: ["public"]`;
   - an exact table filter for the five live application tables so legacy Kysely metadata
     is not introspected or managed;
   - the default separate `drizzle.__drizzle_migrations` metadata location, after verifying
     that the migration role may create/use the `drizzle` schema.
2. On a disposable clone of the current database, run `drizzle-kit pull --init`. Never do
   the first pull against production. Use it to produce a canonical baseline migration and
   introspected definitions.
3. Move and normalize the generated table definitions into:
   - `packages/db/src/schema/auth.ts`
   - `packages/db/src/schema/todo.ts`
   - `packages/db/src/schema/index.ts`
4. Export table objects under Better Auth's expected singular keys: `user`, `session`,
   `account`, and `verification`; export `todoItem` for application code.
5. Use Drizzle 1.0's table-level snake-case mapping or explicit SQL names consistently.
   Do not rely on the removed connection-level casing option.
6. Use timezone-aware PostgreSQL timestamp columns in `Date` mode. Preserve every current
   default, unique constraint, named index, foreign key, and `onDelete`/`onUpdate` action.
7. Export inferred select and insert types from the table objects. Define narrow update
   types for supported mutations rather than a generic update type that permits immutable
   ownership or identity fields.
8. Do not add `defineRelations()` yet. Current repositories use explicit queries, and
   Better Auth joins are not enabled.
9. Run Better Auth's RC schema generator to a temporary output and compare it with the
   canonical auth schema. Resolve differences explicitly; never overwrite the canonical
   schema without review.

**Gate:** the canonical baseline migration creates a fresh database whose application DDL
matches `docs/db-schema.md`, and generating again from the unchanged schema produces no
new migration.

## Phase 3: replace the database resource layer

Rewrite `packages/db/src/client.ts` around `drizzle-orm/node-postgres` and explicit resource
ownership:

- A Node factory creates a `pg.Pool`, initializes Drizzle with the full schema, and returns
  `{ db, close }`.
- A Node singleton getter caches only that process-level resource.
- A Worker factory creates and connects one `pg.Client`, initializes Drizzle with the same
  schema, and returns `{ db, close }` for that request.
- `DB` is the inferred Drizzle database type shared by repositories, auth, and RPC context.
- `checkDatabaseReady()` performs a zero-row or one-row typed query against `user`.

Replace `QueryLoggingPlugin`. Drizzle's default logger exposes SQL and parameters and must
not be enabled. During the spike, choose a supported completion-timing hook at the `pg`
driver boundary and preserve only operation category and duration. If the RC has no safe
completion hook, log duration at focused repository methods and document that Better Auth
query timings are temporarily represented by request/auth timings; do not monkey-patch an
unstable driver API merely for parity.

Update resource consumers:

- `apps/web/src/server/node-server.ts` uses the Node resource and calls `close()` during
  graceful shutdown.
- `apps/web/src/server/cloudflare-worker.ts` awaits creation of the request-scoped Worker
  resource and calls `close()` in `finally`.
- `packages/auth/auth.config.ts` uses a short-lived Node resource for CLI execution and
  closes it when the command process finishes, if the CLI lifecycle permits an explicit
  teardown hook.
- `packages/rpc/src/context.ts` continues to expose only the typed Drizzle `db`, not the
  resource owner.

**Gate:** readiness works in both runtimes, Node shutdown closes its pool, and every Worker
request closes its Hyperdrive-backed client without global request-bound state.

## Phase 4: simplify focused repositories

Delete the Kysely-specific generic layer:

- `packages/db/src/repositories/repository.ts`
- `packages/db/src/repositories/types.ts`

Implement only the methods currently required:

### `TodoRepository`

- `listOwned(userId)` ordered by `createdAt DESC`;
- `create(data)` with `returning()`;
- `updateOwned(userId, id, data)` with both ownership predicates in one update;
- `deleteOwned(userId, id)` with both predicates and a returned ID to distinguish not
  found from success.

### `UserRepository`

- `findById(id)`;
- `updateById(id, data)` with `returning()`;
- `listAdminPage({ page, pageSize })` preserving selected fields, descending creation
  order, total count, and pagination semantics.

Update `packages/db/src/repositories/index.ts` to construct the two focused repositories
without cross-repository injection. Update todo and user RPC handlers to call the focused
method names while preserving their public inputs, outputs, errors, and DTO mapping.

Use Drizzle expressions such as `eq`, `and`, `desc`, and `count` directly. Avoid generic
query-builder callbacks and unsafe `as unknown as` casts. Normalize count values to finite
numbers at the repository boundary.

**Gate:** todo CRUD, admin user listing, and profile updates have the same ordering,
ownership, not-found, conflict, and return-value behavior as before.

## Phase 5: move Better Auth to its Drizzle adapter

1. In `packages/auth/src/server.ts`, replace the Kysely database configuration and
   `CamelCasePlugin` with `drizzleAdapter(options.db, { provider: "pg", schema })`.
2. Pass the explicit schema object so custom table/property mappings are deterministic.
3. Keep existing admin, Expo, cookie, social-provider, trusted-origin, user-field, and
   email/password configuration unchanged unless the Better Auth 1.7 upgrade guide
   requires a targeted adjustment.
4. Do not enable experimental/advanced joins during this migration.
5. Verify the 1.7 custom-scheme trusted-origin behavior for `better-spa://` and the existing
   development `exp://` entries.
6. Verify Better Auth writes still use the existing tables and do not request a schema
   alteration.

**Gate:** sign-up, sign-in, session bootstrap, sign-out, social configuration startup,
admin create/ban/unban/reset-password/impersonation, and Expo-origin handling work against
existing data.

## Phase 6: replace migration and schema-snapshot tooling

1. Retire:
   - `packages/db/kysely.config.ts`;
   - `packages/db/src/migrate.ts` and `packages/db/tsup.migrate.config.ts` if Drizzle Kit
     becomes the sole runner;
   - `packages/db/src/migrations/*.ts` after the canonical Drizzle baseline is committed.
2. Keep the old Kysely migration files available in Git history; do not translate the
   create/drop-job history. The Drizzle baseline represents the current live schema only.
3. Add package/root commands with stable names:
   - `db:generate` -> `drizzle-kit generate`;
   - `db:migrate` -> `drizzle-kit migrate`;
   - `db:check` -> `drizzle-kit check`;
   - retain `db:snapshot`.
4. Keep `db:migrate` as a deployment-time Node command using direct `DATABASE_URL`. Never
   run migrations from a Worker or through a request-time Hyperdrive client.
5. Rewrite `packages/db/src/snapshot.ts` to use parameterized `pg` queries directly rather
   than either ORM. Continue excluding migration metadata from the application schema
   documentation.
6. Update `docs/db-schema.md` only by running `pnpm db:snapshot` after migration state is
   established.
7. Add `pnpm db:check` to the read-only quality gate after confirming the RC command is
   deterministic and noninteractive in CI.

New feature flow after cutover:

1. edit Drizzle table definitions;
2. run `pnpm db:generate --name=<change>`;
3. review the generated `migration.sql` and snapshot;
4. run `pnpm db:migrate` against local PostgreSQL;
5. run `pnpm db:snapshot`;
6. update focused repositories and RPC;
7. run `pnpm check`.

## Phase 7: baseline existing databases safely

Drizzle and Kysely use independent migration metadata. Applying the canonical baseline as
an ordinary pending migration to an existing database would attempt to recreate live
tables and fail.

1. Back up each environment and verify that its DDL matches the canonical baseline.
2. Derive the exact Drizzle 1.0 RC migration metadata record from a disposable database
   initialized by the committed baseline. Do not guess the RC's hash, folder-name, or
   applied-time format.
3. Create a reviewed one-time baselining runbook/script that:
   - creates the configured Drizzle metadata schema/table exactly as the pinned RC expects;
   - records the canonical baseline as already applied;
   - performs no application DDL or data writes;
   - aborts when the existing schema fingerprint differs from the canonical baseline.
4. Rehearse the script on a production-like clone, then baseline staging and production
   before deploying code that uses `drizzle-kit migrate`.
5. Retain `public.kysely_migration` and `public.kysely_migration_lock` during the rollback
   window. They are inert and allow the previous application revision to operate.
6. After the rollback window, optionally remove the legacy metadata in an explicit,
   reviewed Drizzle migration. Do not mix that cleanup into the ORM cutover.

For a brand-new database, run the committed Drizzle baseline normally; do not baseline it
as already applied.

## Phase 8: build boundaries, documentation, and cleanup

- Replace `kysely` with `drizzle-orm` in TanStack Start import-protection rules in
  `apps/web/vite.config.ts` and `apps/web/vite.worker.config.ts`.
- Keep `pg` external where required; verify whether Drizzle should remain bundled rather
  than adding it to SSR externals.
- Update `scripts/validate-workspace.mjs` so browser code cannot import Drizzle or the DB
  package.
- Update `knip.json` from `kysely.config.ts` to `drizzle.config.ts`.
- Update exports and comments in `packages/db/src/index.ts`, health routes, and
  `apps/web/src/lib/orpc.ts`.
- Update `AGENTS.md`, `README.md`, `docs/database-repository.md`,
  `docs/rpc-architecture.md`, `docs/cloudflare.md`, `docs/development-guides.md`,
  `docs/commands.md`, and `docs/devops.md` to make Drizzle and generated SQL migrations
  canonical.
- Update `packages/db/src/repositories/README.md` for focused repositories and inferred
  schema types.
- Remove all runtime and direct dependency references to Kysely. Historical planning docs
  may retain historical wording only if clearly marked as superseded.

## Cutover order

1. Freeze schema changes and back up the database.
2. Complete the code migration and validate it against a cloned existing database.
3. Commit the canonical Drizzle baseline and exact RC lockfile.
4. Baseline Drizzle migration metadata in staging; deploy and smoke-test staging.
5. Baseline production migration metadata.
6. Deploy the Drizzle application revision without application DDL changes.
7. Monitor auth failures, PostgreSQL errors, connection counts, request latency, and Worker
   logs.
8. Keep the prior revision deployable and Kysely metadata intact through the rollback
   window.
9. Resume schema changes only after the cutover is accepted.

Rollback before the first post-cutover schema migration is a code rollback: redeploy the
previous Kysely revision. The application schema is unchanged and Kysely metadata remains.
After a Drizzle-only schema migration, rollback requires a migration-specific database
plan and is no longer automatically safe.

## Validation checklist

Run against both a fresh database and a clone containing existing users/sessions/todos:

```bash
pnpm db:migrate
pnpm db:snapshot
pnpm auth:generate
pnpm check
pnpm build:node
pnpm build:worker
pnpm worker:dry-run
```

Then perform runtime smoke checks:

- `/api/health/live` and `/api/health/ready` on Node and Worker preview;
- email/password sign-up, sign-in, session restore, and sign-out;
- profile update and uniqueness conflict;
- todo list/create/update/delete, including cross-user update/delete rejection;
- admin list/create/ban/unban/reset-password/impersonation;
- existing session and account rows remain readable;
- Worker connection is closed on success and failure;
- no SQL parameters, auth tokens, passwords, cookies, or database URLs appear in logs.

Final repository checks:

- `rg -n "kysely|Kysely"` returns only intentional historical references;
- unchanged schema generation produces no migration;
- `docs/db-schema.md` shows no unintended application DDL change;
- `pnpm check:full` passes.

## Stop conditions

Do not cut over if any of these remain unresolved:

- Better Auth packages require incompatible Drizzle peers;
- canonical baseline differs from an environment's schema;
- migration metadata cannot be baselined without application DDL;
- Better Auth generation requests an unexplained schema change;
- Node pool or Worker client ownership is ambiguous;
- Worker build requires global request-bound database state;
- repository rewrites weaken ownership predicates or conflict handling;
- query logging exposes SQL parameters or credentials.
